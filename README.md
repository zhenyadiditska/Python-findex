# findex — Лабораторні роботи 1–4

[![CI](https://github.com/zhenyadiditska/Python-findex/actions/workflows/ci.yml/badge.svg)](https://github.com/zhenyadiditska/Python-findex/actions/workflows/ci.yml)

## Опис проєкту

Findex — це пошукова система для аналізу текстових документів, написана мовою Python.

Проєкт розвивався протягом чотирьох лабораторних робіт. У ньому реалізовано потокову обробку тексту, токенізацію, інвертований індекс, Boolean-пошук, ранжування результатів, парсер запитів, кешування, автоматичне тестування та командний інтерфейс CLI.

Для роботи з проєктом використовуються Python 3.14 та менеджер залежностей uv.

## Текстовий корпус

Корпус містить 1218 текстових документів загальним розміром приблизно 25 MB.

Джерела документації:

- Python 3.14: https://docs.python.org/3.14/
- Django 6.0: https://docs.djangoproject.com/

Також до корпусу додано кілька власних тестових документів.

Папка `data/` виключена з Git за допомогою `.gitignore`.

## Лабораторна робота 1 — Аналіз текстового корпусу

### Правила токенізації

Для нормалізації тексту використовується Unicode NFC та метод `casefold()`.

Основні правила:

- Усі слова переводяться в нижній регістр.
- Розділові знаки ігноруються.
- Апострофи всередині слів зберігаються.
- Дефіси всередині слів зберігаються.
- Цифри можуть бути частиною токенів.
- Символ підкреслення вважається роздільником.

Приклади:

- `Python` → `python`
- `front-end` → `front-end`
- `don't` → `don't`
- `Python3` → `python3`
- `web_dev` → `web`, `dev`

### Запуск аналізу

Потокова версія:

```bash
uv run python -m findex.stats
```

Версія з попереднім завантаженням даних:

```bash
uv run python -m findex.greedy
```

### Порівняння продуктивності

Обидві версії перевірялися на однаковому корпусі.

| Показник                   |    Streaming |        Greedy |
| -------------------------- | -----------: | ------------: |
| Кількість документів       |         1218 |          1218 |
| Загальна кількість токенів |    2 857 461 |     2 857 461 |
| Унікальні токени           |       56 895 |        56 895 |
| Час виконання              |   5.286473 с |    4.076011 с |
| Пікова пам'ять             | 38 205.19 KB | 179 987.69 KB |

### Висновки

Потокова версія обробляє документи по одному та не зберігає всі документи й токени у списках.

Greedy-версія спочатку завантажує всі документи та токени в пам'ять. Через це вона використовує значно більше ресурсів.

Під час тестування Greedy-версія працювала швидше, але використовувала приблизно у 4,7 раза більше пам'яті.

Отже, потокова обробка є ефективнішою з погляду використання пам'яті, особливо під час роботи з великими текстовими корпусами.

## Лабораторна робота 2 — Інвертований індекс

### Побудова індексу

У другій лабораторній роботі було реалізовано інвертований індекс.

Він зберігає інформацію про те, у яких документах зустрічається певне слово та скільки разів воно там з'являється.

Для зберігання даних використовуються два класи:

- `Posting` — містить ідентифікатор документа та частоту слова.
- `DocMeta` — містить ідентифікатор документа, шлях до нього та кількість токенів.

Обидва класи створені за допомогою `dataclass(frozen=True, slots=True)`.

Індекс будується за один прохід через документи. Для збирання частот використовується `defaultdict` разом із `Counter`. Списки postings для кожного слова сортуються за ідентифікатором документа.

### Boolean-пошук

Реалізовано три логічні операції:

- `AND` — знаходить документи, у яких є обидва слова.
- `OR` — знаходить документи, у яких є хоча б одне з двох слів.
- `NOT` — знаходить документи, у яких є перше слово, але немає другого.

Для пошуку реалізовано два способи:

1. `merge` — порівняння двох відсортованих списків за допомогою двох покажчиків.
2. `set` — використання множин для пошуку спільних або різних документів.

За замовчуванням використовується `merge`. Також можна вибрати потрібний алгоритм за допомогою параметра `--engine`.

### Збереження індексу

Для збереження та завантаження індексу реалізовано два формати:

- `pickle` — зберігає об'єкти Python у бінарному файлі `index.bin`.
- JSON — зберігає дані у текстовому файлі `index.json`.

Формат JSON зручний тим, що його можна переглянути звичайним текстовим редактором. Файл `pickle` займає менше місця та швидше завантажується в проведеному тесті.

Важливо: файли `pickle` не можна завантажувати з невідомих або ненадійних джерел.

## Лабораторна робота 3 — Ранжування та об'єктна модель

### 1. Модель індексу

Клас `Index` надає:

- `__len__`, `__contains__`, `__getitem__`, `__iter__`, `__repr__`;
- `num_docs`, `avg_doc_length`, `doc_length()` та `df()`;
- `open_index()` як контекстний менеджер.

### 2. Ранжування результатів

Реалізовано два алгоритми:

- TF-IDF;
- BM25 з параметрами `k1=1.5` та `b=0.75`.

Результати зберігаються в `SearchResult`, а найкращі документи вибираються за допомогою `heapq.nlargest()`.

### 3. Парсер пошукових запитів

Парсер підтримує:

- `AND`, `OR` та `NOT`;
- неявний `AND` між сусідніми термінами;
- круглі дужки;
- пошук фраз у лапках.

Приклад:

```text
python AND (async OR await) NOT java "event loop"
```

### 4. Кешування, декоратори та фрагменти тексту

- `@timed` вимірює час виконання функції.
- `lru_cache(maxsize=256)` зберігає результати запитів у кеші.
- `make_snippet()` створює фрагмент тексту та виділяє знайдені слова.

### 5. Експерименти з ранжуванням

Індекс містить 1218 документів і 56 895 унікальних термінів.

Було проведено три перевірки:

1. Рідкісний термін `flask` (DF=1) отримав вищу оцінку, ніж поширений термін `in` (DF=1176).
2. У BM25 різниця оцінок між 19-м та 20-м повторенням терміна становила приблизно 0.00011.
3. Для терміна `models`, який зустрічається по одному разу в обох документах, короткий документ отримав оцінку 2.7183, а довгий — 0.0244.

### 6. Оцінювання якості пошуку — Precision@5

Було перевірено 10 запитів із вручну визначеною релевантністю документів.

| Запит            |   TF-IDF |     BM25 |
| ---------------- | -------: | -------: |
| python           |     0.80 |     1.00 |
| django           |     1.00 |     1.00 |
| async            |     1.00 |     1.00 |
| database         |     1.00 |     1.00 |
| security         |     0.60 |     1.00 |
| testing          |     0.80 |     0.60 |
| template         |     1.00 |     1.00 |
| request          |     0.60 |     1.00 |
| class AND method |     0.80 |     1.00 |
| "event loop"     |     0.60 |     0.80 |
| **Середнє**      | **0.82** | **0.94** |

У цьому експерименті BM25 отримав вищий середній Precision@5, ніж TF-IDF. Результати залежать від ручної оцінки релевантності документів.

## Лабораторна робота 4 — Типи, тести, пакування і CLI

### 1. Типізація

Для публічних функцій і методів використано анотації типів.

Також реалізовано:

- `Protocol` для опису інтерфейсу алгоритмів ранжування.
- `Literal` для обмеження допустимих значень параметрів.
- `Iterator` та `Iterable` для генераторів і послідовностей.
- Строгий режим перевірки типів Pyright (`typeCheckingMode = "strict"`).

### 2. Тестування

Для тестування використовується `pytest`, а для перевірки властивостей — `Hypothesis`.

Реалізовано тести для:

- токенізації, включно з Unicode;
- побудови індексу;
- Boolean-пошуку та парсера запитів;
- пошукових алгоритмів;
- створення snippets;
- збереження та завантаження індексу;
- властивостей індексу та операцій merge;
- команд CLI.

Також перевіряються властивості:

- після збереження та завантаження індекс залишається таким самим;
- postings залишаються відсортованими;
- результат merge відповідає операціям над множинами.

### 3. CLI

Для роботи з пошуковою системою створено командний інтерфейс на основі Typer та Rich.

Доступні команди:

- `findex index` — створення та збереження індексу з папки документів;
- `findex search` — пошук документів за запитом;
- `findex stats` — статистика текстового корпусу.

Команда пошуку підтримує TF-IDF і BM25, налаштування кількості результатів та формат JSON.

### 4. Встановлення та запуск

Для встановлення залежностей:

```bash
uv sync --locked
```

Створення індексу:

```bash
uv run findex index
```

За замовчуванням документи читаються з папки `data`, а індекс зберігається у файлі `index.bin`.

Можна вказати власну папку та файл:

```bash
uv run findex index ./data -o index.bin
```

Пошук:

```bash
uv run findex search "python"
```

Пошук із BM25:

```bash
uv run findex search "python" --scorer bm25
```

Обмеження кількості результатів:

```bash
uv run findex search "python" -k 5
```

Виведення результатів у JSON:

```bash
uv run findex search "python" --json
```

Статистика корпусу:

```bash
uv run findex stats
```

Довідка CLI:

```bash
uv run findex --help
```

### 5. Перевірки якості коду

У проєкті використовуються:

- Ruff — перевірка стилю та помилок у коді.
- Pyright — статична перевірка типів.
- Pytest — автоматичні тести.
- Coverage.py — вимірювання покриття коду тестами.

Команди перевірки:

```bash
uv run ruff check .
uv run pyright
uv run pytest
```

Вимірювання покриття:

```bash
uv run coverage run -m pytest
uv run coverage report -m
```

### 7. Continuous Integration

Для автоматичної перевірки використовується GitHub Actions.

Workflow запускається під час `push` та `pull_request` і виконує:

1. Встановлення Python та uv.
2. Встановлення залежностей із `uv.lock`.
3. Перевірку Ruff.
4. Перевірку Pyright.
5. Запуск тестів Pytest.

## Обмеження проєкту

- Поточне покриття коду тестами становить 86%, тому не всі гілки виконання перевірені.
- Найменше покриття мають модулі `index.py` (62%), `search.py` (71%) та `cli.py` (75%).
- Оцінка Precision@5 базується на вручну визначеній релевантності документів.
- Для роботи з власним корпусом потрібно самостійно підготувати папку з текстовими документами.
